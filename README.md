## 📌 О проекте и проблематика

**autoXAK (АвтоХАК)** — программный комплекс класса **Zero-Hardware Telematics**, разработанный в рамках Центра технологического предпринимательства «ПУСК» МФТИ (научные специальности ВАК РФ: **2.3.1** — «Системный анализ, управление и обработка информации» и **2.5.11** — «Наземные транспортно-технологические средства»).

### Назначение

Приложение сохраняет реальные наблюдения смартфона независимо от доступности
сети и пригодности данных для расчёта. Масло, расход топлива и экономия требуют
собственных исходных данных и проверяемой модели. Движение телефона само по себе
не измеряет температуру двигателя, химическое состояние масла или сбережённые литры.

## ⚡ Ключевые возможности

- Независимая запись GPS/IMU с фактическими временными метками и признаками качества.
- IndexedDB, черновики, повторная отправка и история без дублирования поездок.
- Численное интегрирование скорости и пересечений порогов по реальному времени.
- Баланс работы на колёсах с явно заданными массой, вращающейся инерцией,
  уклоном, ветром, плотностью воздуха, сопротивлением качению и CdA.
- Интегрирование измеренного топливного потока и явно переданной карты ДВС,
  без экстраполяции за её границы.
- Знаковое сравнение топлива сопоставимых наблюдений, с явной ценой и
  необязательными объявленными границами погрешности. Это не автоматическое начисление.
- Отдельный исследовательский прогноз расхода на VED/CatBoost; его ограничения
  и происхождение описаны в [FUEL_MODEL.md](docs/FUEL_MODEL.md).

## 🔬 Физико-математическое ядро (Wear & Cost Engine)

Код численных функций: `app/services/reference_math.py`. В нём нет базовых
«1,8 л экономии на 100 км», множителей износа по пробкам, рублёвого штрафа
за каждый манёвр или заданного всем водителям суточного расхода.

Расстояние вычисляется интегралом скорости по реальным временным меткам.
Механическая работа разделяется на изменение кинетической энергии,
качение, потенциальную энергию и аэродинамическую работу. Тяговая и отрицательная
работа интегрируются раздельно. Механическая энергия не подменяется литрами.

Для заданных кусочно-линейных наблюдений интегралы вычисляются аналитически;
для билинейной карты расхода интервалы разбиваются по границам ячеек.
Неизвестные параметры не заполняются параметрами случайного автомобиля.

Это продольная модель в пределах явно описанного контракта, а не полная
термодинамическая или многотельная модель автомобиля. Неизвестные уклон,
ветер, карты ДВС и состояние масла нельзя восстановить добавлением формул.

## 📊 Метрологическая верификация и доказательство гипотезы H1

**Дорожная точность не подтверждена.** Реальных парных контрольных логов у
проекта пока нет. Совпадение двух синтетических формул, p-value по расчётным
рублям или обороты, делённые на 800, не подтверждают модель износа масла.

Проверяются аналитические ответы, сохранение энергии, размерности, знаки,
независимость от разбиения временной сетки, защита от экстраполяции и
сохранность исходных данных. Сравнение с наблюдениями возвращает MAE/RMSE,
WAPE, смещение и число нулевых эталонных значений. Проверяется отсутствие
повторных поездок и пересечения объявленных автомобилей обучения/проверки.

Новые API: `/api/v3/math/evaluate`, `/api/v3/math/compare-fuel`,
`/api/v3/math/validate-fuel`. Все требуют авторизации и не начисляют деньги.
Источник, параметры, хеш и результат анализа поездки можно сохранить вместе
с ней через `reference_math`; сведения доступны только владельцу.

## 🏗 Архитектура системы и конвейер данных

GPS/IMU → валидация и локальная очередь → атомарное сохранение → история.
Наблюдения с достаточным качеством → кинематика и диагностические события.
Явные параметры/карты/контрольные данные → численное ядро → версионированные
результаты и доказательная база. Ошибка дополнительных расчётов не превращает
недостоверные величины в нули и не удаляет корректную сырую запись.

Старые балансы и результаты не переписываются. Они остаются архивными
оценками прежней версии и не приобретают подтверждённую точность после обновления.

## 🚀 Быстрый старт и локальное развертывание

Для публичного сервера используйте [инструкцию боевого развертывания](docs/PRODUCTION.md)
и отдельный `compose.production.yml`. Для существующего Nginx и базы описан
переход с сохранением тома, ключей, резервной копией и возвратом при ошибке.

### 1. Системные требования
* **Docker Desktop** версии 24.0+ с поддержкой Compose V2;
* Мобильный браузер (Safari iOS 14.5+ или Chrome Android 90+) с поддержкой Generic Sensor API.
* *Важно:* Доступ к аппаратным сенсорам движения (акселерометр/гироскоп) на смартфонах жестко заблокирован по небезопасному протоколу HTTP. Сервер по умолчанию поднимается по протоколу **HTTPS**.

### 2. Клонирование репозитория
```bash
git clone https://github.com/kodeandr/autoXAK.git
cd autoXAK
```

### 3. Конфигурация окружения (.env)
Создайте файл `.env` в корневой директории:
```env
# Generate each value locally, e.g. python -c "import secrets; print(secrets.token_hex(32))"
SECRET_KEY=<private persistent random value, at least 32 characters>
POSTGRES_PASSWORD=<separate private random value>
DGIS_USE_MOCK=true
DGIS_API_KEY=
YANDEX_CLIENT_ID=
YANDEX_CLIENT_SECRET=
YANDEX_REDIRECT_URI=https://autoxak.ru/api/v1/auth/yandex/callback
```

### 4. Генерация локальных SSL-сертификатов
Для обеспечения работы датчиков смартфона в локальной сети выпустите самоподписанную пару сертификатов:
```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout key.pem -out cert.pem \
  -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

### 5. Запуск комплекса в Docker Compose
```bash
docker compose up --build -d
```
Убедитесь, что все три контейнера перешли в рабочее состояние:
```bash
docker compose ps
```
*Контейнеры `autoXAK_backend_api` и `autoXAK_redis` должны иметь статус `Up`, а `autoXAK_postgres` — `Up (healthy)`.*

### 6. Первичная инициализация БД (Seeding)
Выполните наполнение базы данных нормативным каталогом автомобилей и региональными ценами на топливо:
```bash
# Наполнение каталога ТС с паспортными характеристиками
docker compose exec api python seed_fleet.py

# Наполнение матрицы региональных цен АЗС
docker compose exec api python seed_fuel_prices.py
```

### 7. Проверка работоспособности
```bash
curl --cacert cert.pem "https://localhost:8000/health"
```
Ожидаемый ответ сервера:
```json
{"status":"ok","service":"autoXAK Fuel Autonomy & Wear Engine","engine":"Reference mathematics and durable recordings","version":"2.0.0"}
```

## 🧪 Запуск метрологической верификации

На отдельной тестовой PostgreSQL БД:

```bash
python -m pytest tests/test_reference_math.py
python -m scripts.benchmark_suite examples/reference_math/validation.json
```

Пример намеренно синтетический и не является контрольной поездкой. Для своих
данных используйте тот же JSON-контракт с настоящими источниками, ID поездок,
автомобилей и объявленным набором обучения. Скрипт не генерирует псевдореальные
наблюдения и не объявляет научную гипотезу подтверждённой.

`run_verification.py` и `run_multicar_verification.py` — только синтетические
проверки интерфейса. Старые `calibrate_verification.py`, `scripts/verify_model.py`
и `scripts/match_obd_db.py` больше не выполняют псевдоверификацию масла.

## 📱 Клиентский интерфейс (PWA & Safety HUD)

Разметка и CSS сохранены. Главный экран показывает состояние записи и
накопленный архивный баланс. Неподтверждённые показатели масла, денег и
универсального индекса показываются как «—».

Во время поездки работают сбор датчиков, GPS, локальная очередь и поддерживаемое
браузером удержание экрана. Итог подтверждает сохранение записи; без
подтверждённой экономии зачисление не обещается. История сохраняет поездки
с доступными измерениями и признаками качества. Конфигуратор сохраняет
известные параметры автомобиля, цену топлива и стоимость обслуживания.

## Проверки после аудита

Проверки API с пользовательскими данными требуют Bearer-токен. `user_id`, отпечаток
устройства и идентификатор гостя не подтверждают право доступа. Яндекс OAuth требует
настроенных переменных; демо отключено по умолчанию. `ENABLE_YANDEX_DEMO=true`
предназначен только для изолированной разработки.

После обновления замените ранее опубликованные ключи 2ГИС/Яндекса, пароли БД и TLS
ключ: удаление значений из файлов не отзывает их. Сгенерируйте собственную пару
`key.pem`/`cert.pem` по инструкции выше. Они исключены из Git. `SECRET_KEY` должен
сохраняться между перезапусками. Перед ротацией подписи учтите, что старые токены
перестанут действовать; для стабильных Яндекс ID сохраните отдельный `YANDEX_ID_SALT`.

Установите зависимости из `requirements.txt`. Запускайте `python -m pytest` из корня
с `DATABASE_URL`, направленным на отдельную тестовую PostgreSQL БД, и заданным
`SECRET_KEY`. Тесты запросов откатывают свои транзакции; проверки конкуренции
создают и удаляют собственных пользователей. Доступность PostgreSQL обязательна.

Браузерные регрессии: `cd tests/browser && npm ci && npm test`. Нужны запущенный API
и Chromium (`CHROMIUM_PATH=/path/to/chromium`), адрес задаётся `AUTOXAK_BASE_URL`
(по умолчанию внутренний HTTP loopback, порт 8000). Эти тесты создают собственных
гостей и поездки; запускайте их в БД разработки. При отсутствии системного Chromium
можно установить браузер средствами Playwright из официального источника.

Скрипты `run_verification.py` и `run_multicar_verification.py` проверяют интерфейс
на синтетических сигналах и не доказывают дорожную точность. Синтетическая
калибровка масла больше не поддерживается. По умолчанию они используют локальный HTTPS и
доверяют локальному `cert.pem`; `AUTOXAK_CA_FILE` задаёт собственный CA,
`AUTOXAK_TOKEN` — существующую сессию. Для внутренней проверки без TLS явно задайте
`AUTOXAK_BASE_URL=http://127.0.0.1:8000`. Отключение проверки сертификатов не требуется.

Статистические отчёты не подтверждают гипотезу по одному совпадению или синтетическим рублям.
Нулевой знаменатель WAPE/MAPE даёт `null`, а не вымышленную точность.
Оценки топлива/износа остаются исследовательскими; аппаратные датчики смартфонов,
живые интеграции и реальная точность требуют отдельных испытаний.
