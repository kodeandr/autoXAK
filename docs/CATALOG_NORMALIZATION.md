## Реализованный инструмент

`app/services/catalog_normalization.py` содержит детерминированную нормализацию.
CLI находится в `app/cli/normalize_vehicle_catalog.py`; доступен также запуск
`python -m scripts.normalize_vehicle_catalog` из репозитория.

Поддерживаемые входы:

- `carsbase_taxonomy`: JSON-снимок марок/моделей;
- `legacy_seed`: литерал `TOP_FLEET_DATA` из Python-файла;
- `legacy_tree`: JSON-выгрузка серверного каталога;
- `frontend_fallback`: литерал `FALLBACK_CATALOG` внутри HTML.

Python и JavaScript из входных файлов не исполняются. Парсер frontend принимает
только используемое здесь подмножество литералов; выражения/вызовы отклоняются.
Переименование `mass_kg` → `curb_weight_kg`, `fuel_rate` →
`base_city_fuel_rate_l100km` касается только исходных заявлений браузерного
справочника, не подтверждает паспортный характер этих значений.

Контроль:

- Точный SHA-256 исходных байтов и обязательный манифест происхождения.
- Unicode NFC и пробелы в названиях; исходные внешние ID не переписываются.
- Стабильные собственные ID для внешней таксономии; прежние ID моделей и
  вариантов проекта сохранены. Изменение ревизии не меняет идентичность.
- Дубли JSON-ключей, NaN/Infinity, численное переполнение, неверные типы,
  непоследовательные годы и связи отклоняются либо помещаются в отчёт брака.
- Противоречащие строки с одним ID изолируются все; первая строка не становится
  победителем. Точные повторы сворачиваются с записью об этом в отчёте.
- Совпадение нормализованных названий не объединяет разные ID.
- Неизвестные поля источника отражаются как изменение схемы и остаются в снимке.
- Неизвестные значения не заменяются 0, расходом 8,2, массой 1500 или условным
  масляным ресурсом. Класс автомобиля не превращается в тип кузова или CdA.
- Поисковые соответствия привязаны к хешу снимка и конкретным внешним ID;
  карта не может незаметно сослаться на другую марку или другой снимок.

На выходе: исходные байты, манифест, нормализованный JSON, список проблем,
поисковые кандидаты, сравнение legacy-источников, контрольные суммы файлов.
Директории создаются с правами 0700, файлы — 0600; существующие результаты
не перезаписываются. `COMPLETE.json` пишется последним. Без него результат
следует считать незавершённым. Наличие COMPLETE не является аттестацией точности.
Код завершения 1 у нормализатора означает ошибки в строках/параметрах,
2 — ошибку входа/запуска. Предупреждения и межисточниковые конфликты остаются
в отчёте при успешном завершении обработки; успешный запуск не разрешает импорт.

## Воспроизведение

Из корня репозитория, в окружении проекта:

```bash
python -m app.cli.normalize_vehicle_catalog \
  --input seed_fleet.py \
  --manifest catalog/sources/legacy_seed.source.json \
  --output-dir /tmp/autoxak-seed-review

python -m app.cli.normalize_vehicle_catalog \
  --input static/setup.html \
  --manifest catalog/sources/frontend_fallback.source.json \
  --compare-review /tmp/autoxak-seed-review/normalized.json \
  --output-dir /tmp/autoxak-frontend-review
```

Для внешнего снимка использовать точную ревизию из
`catalog/sources/carsbase.source.json`, затем:

```bash
python -m app.cli.normalize_vehicle_catalog \
  --input /PATH/TO/cars.json \
  --manifest catalog/sources/carsbase.source.json \
  --coverage docs/data/vehicle_catalog_priorities.csv \
  --aliases catalog/carsbase.search_candidates.json \
  --output-dir /tmp/autoxak-carsbase-review
```

Заменить только путь к скачанному снимку. Если SHA-256 изменился, сначала
проверить новый источник и его манифест, не отключать проверку целостности.
При повторном запуске выбрать новую выходную директорию.

## Снимок каталога на действующем сервере без обновления приложения

Экспортёр `app/cli/export_vehicle_catalog.py` самодостаточен и может выполняться
через stdin в старом API-контейнере. Читает только `vehicle_makes`,
`vehicle_models`, `vehicle_trims` в одной транзакции PostgreSQL
`REPEATABLE READ, READ ONLY`. Проверяет фактическое включение режима только
чтения. Пользователи, поездки, пароли и строки подключения не экспортируются.

На HOSTKEY, в Bash:

```bash
cd /opt/autoxak-production &&
git fetch origin feat/catalog-data-normalization &&
git show FETCH_HEAD:app/cli/export_vehicle_catalog.py > /tmp/autoxak-export-catalog.py &&
docker compose --env-file .env.production -f compose.production.yml exec -T api \
  python /app/deploy/entrypoint.py python - \
  --output-dir /tmp/autoxak-catalog-snapshot \
  < /tmp/autoxak-export-catalog.py
```

Обёртка `entrypoint.py` нужна для существующей конфигурации доступа к БД;
прямой `docker exec python` может не получить сформированный `DATABASE_URL`.
`git fetch` не переключает ветку, не запускает миграции и не перезапускает API.
Экспортёр откажется перезаписывать существующую `/tmp/autoxak-catalog-snapshot`.

Скопировать результат на хост:

```bash
mkdir -m 700 /root/autoxak-catalog-audit
docker cp autoxak-production-api-1:/tmp/autoxak-catalog-snapshot \
  /root/autoxak-catalog-audit/
```

Для проверки этой выгрузки использовать её `catalog.json` и `source.json` как
`--input` и `--manifest`. До этого результаты проверки файлов репозитория нельзя
называть проверкой фактической боевой БД.

## Что применено

Сформированы нормализованные наборы и отчёты, добавлены воспроизводимые
инструменты и 31 новая проверка. Вся Python-проверка: 208 тестов прошли,
один тест отдельного staging пропущен. Проверки экспорта используют PostgreSQL:
контролируют отсутствие DML при чтении, полноту строк и сохранение пользователей
и поездок. Внешний carsBase-набор проверен отдельно по зафиксированному снимку;
тесты не зависят от доступности внешней сети.

Исходные большие внешние выгрузки и их нормализованные копии хранятся приватно,
не опубликованы в GitHub. Условия использования carsBase для рабочего продукта
остаются неустановленными. Нормализатор не имеет команды публикации в БД:
изменение `license_status` не включает скрытый импорт.

Рабочий каталог, ORM-схема, расчёты приложения, пользовательские профили,
поездки и дизайн не менялись. Следующий этап применения данных — отдельная
миграция каталога и импорт с проверенным происхождением и условиями использования.
