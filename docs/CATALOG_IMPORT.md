# Подключение нормализованного каталога без замены существующих автомобилей

Реализация подготовлена поверх `main` с исправлениями поездок (`727158c`) и
ветки `feat/catalog-data-normalization`. Само обновление кода не загружает
внешние данные и не включает новый каталог автоматически.

## Что меняется

Добавляются три отдельные таблицы:

- `catalog_imports`: неизменяемый снимок, происхождение и список марок;
- `catalog_models`: модели этого снимка, без выдуманных модификаций и физических параметров;
- `catalog_state`: указатель на активный снимок.

`vehicle_makes`, `vehicle_models`, `vehicle_trims`, существующие `car_id`,
профили, поездки и накопления импортёр не перезаписывает. Полная проверка
сравнивает прежние строки этих таблиц до/после загрузки 5000 тестовых моделей.
Загрузка выполняется транзакционно; повтор того же снимка не создаёт дубликаты.
Активация — отдельное атомарное переключение; предыдущий снимок сохраняется.
Блокировка DDL согласована с блокировкой инициализации приложения, импорт и
активация сериализуются отдельной advisory-блокировкой PostgreSQL.

Существующий `GET /api/v1/vehicles/catalog` не меняет контракт. Новые маршруты:

| Маршрут | Результат |
|---|---|
| `GET /api/v1/vehicles/catalog/taxonomy/makes` | Марки активного снимка с количеством моделей |
| `GET /api/v1/vehicles/catalog/taxonomy/models?make_id=...&snapshot_id=...&limit=200&offset=0` | Модели выбранной марки, порциями до 500 |
| `GET /api/v1/vehicles/catalog/taxonomy/models/{car_id}` | Восстановление ранее выбранной модели |

Модели догружаются при выборе марки; весь массив 4952 моделей не отправляется
в стартовой странице. Пагинация привязана к снимку: при смене версии возвращается
409, а не смесь разных версий. Отказ дополнения оставляет прежний каталог доступным.
Поздний ответ не сбрасывает изменённые расход или модификацию прежнего автомобиля.

## Выбор автомобиля и расчёты

У существующих автомобилей сохраняются доступные модификации. У внешней модели
без модификаций показывается «Модификация не указана» и требуется городской
расход, введённый пользователем. Масса, двигатель, КПД и другие неизвестные
параметры остаются `null`; условная «базовая модификация» не создаётся.

Новый `car_id` имеет отдельное пространство `catalog_model_<UUID>` и не заменяет
старые идентификаторы. В пользовательском профиле фиксируется выбранная модель
и объявленный расход. Сервер считает рубли по существующей политике TwinEngine
с этим расходом и ценой пользователя. Формула, пороги датчиков и логика записи
не изменяются. Деактивация каталога не отбирает ранее сохранённый выбор и не
удаляет возможность сохранить следующую поездку с уже заполненным профилем.

## Сначала восстановить действующий сервер

На обследованном HOSTKEY действующий проект — `/opt/autoxak`, контейнеры
`autoXAK_backend_api`, `autoXAK_postgres`, том `autoxak_pgdata`; HTTPS завершает
Nginx, который направляет HTTP на `127.0.0.1:8000`. У второго
`autoxak-production-postgres-1` обнаружен тот же том. Одновременный запуск двух
PostgreSQL на одном PGDATA недопустим.

Импорт выполняется после восстановления API и подтверждения `/ready`. Перед
импортом проверьте, что только один PostgreSQL использует этот том, и создайте
проверенный резервный дамп. Не запускайте параллельно другой Compose-проект,
который ссылается на тот же PGDATA. Настройки тестового приложения с отдельной
БД не требуется менять.

## Происхождение и разрешение использования

`carsbase.source.json` сейчас содержит `license_status: unresolved`. Для
зафиксированного снимка план распознаёт 426 марок и 4952 модели, но сообщает
`can_load: false`. Импортёр не загружает и не активирует такой источник.
Нормализация или нулевое число ошибок не устанавливают права использования.

Для рабочего импорта необходим источник с установленными условиями:
`licensed` или собственные данные `project_license` и действительное основание
в `license_evidence`. Не следует просто переименовывать статус, оставляя
неустановленные права. После изменения подтверждённого манифеста пакет
нормализуется заново: исходный снимок, манифест и результат должны согласоваться.
Внешние исходные данные не включены в GitHub и Docker-образ.

## Проверка и сборка пакета

Используется законченный пакет нормализатора с `COMPLETE.json`, контрольными
суммами, `source.snapshot`, `source.manifest.json`, `normalized.json`. Более
старый пакет без `files_sha256` необходимо пересобрать текущим нормализатором.
Импортёр перепроверяет все хеши и повторно получает normalized из исходных байтов;
редактирование `normalized.json` с пересчётом его хеша проверку не обходит.
Повреждённые, частично отклонённые или пустые наборы отклоняются целиком.

В окружении Python проекта:

```bash
python -m app.cli.normalize_vehicle_catalog \
  --input /private/catalog/source.snapshot \
  --manifest /private/catalog/approved.source.json \
  --output-dir /private/catalog/review-v1

python -m app.cli.import_vehicle_catalog plan /private/catalog/review-v1
```

`plan` не подключается к БД, не создаёт таблицы и не записывает данные. Проверка
этого свойства запускает CLI с недоступным адресом PostgreSQL. Размер каждого
файла пакета ограничен 16 MiB; пути за пределами пакета и симлинки отклоняются.
Вывод плана содержит идентификатор снимка, количества, статус источника и
готовность загрузки. Сохраните `snapshot_id`.

## Тестовая среда и применение на текущем сервере

Сначала запустите команды на отдельном тестовом Compose-проекте с отдельным
томом PostgreSQL. Подставьте его собственный Compose-файл/проект. Ниже команды
для действующего `/opt/autoxak`; выполнять их следует после проверки в тестовой
среде, резервирования и обновления кода до ветки с интеграцией.

Пакет хранится **на сервере** в `/root/autoxak-catalog/review-v1`, права доступа
ограничены владельцем. Одноразовый контейнер читает его через read-only mount,
не публикует порты API и не запускает дополнительные PostgreSQL/Redis:

```bash
cd /opt/autoxak

# Предварительный просмотр, ещё без записи.
docker compose -p autoxak run --rm --no-deps --user 0 \
  -v /root/autoxak-catalog/review-v1:/review:ro \
  api python -m app.cli.import_vehicle_catalog plan /review

# Загрузить разрешённый снимок; в интерфейсе он пока не появится.
docker compose -p autoxak run --rm --no-deps --user 0 \
  -v /root/autoxak-catalog/review-v1:/review:ro \
  api python -m app.cli.import_vehicle_catalog load /review

# Просмотр загруженных снимков.
docker compose -p autoxak run --rm --no-deps --user 0 \
  api python -m app.cli.import_vehicle_catalog status

# Включить проверенный snapshot_id из вывода plan/load.
docker compose -p autoxak run --rm --no-deps --user 0 \
  api python -m app.cli.import_vehicle_catalog activate SNAPSHOT_ID
```

Во втором тестовом окружении проверьте прежний автомобиль, новую модель с
введённым расходом, старт/завершение поездки, начисление/повторную отправку,
историю и возврат на прежний каталог. API-процесс не нужно перезапускать для
активации: следующий запрос читает текущий указатель. Открытую страницу гаража
следует обновить, чтобы получить новый список марок.

Для production Compose с собственным env-файлом используются те же команды
`run` с правильными `--env-file`, `-f` и именем проекта, а не новый проект поверх
того же тома. Его entrypoint сам формирует строку доступа к БД из переменных.
Указание `--user 0` относится к одноразовому обслуживающему контейнеру для чтения
закрытого пакета; пользователь постоянно работающего API не меняется.

## Откат

Для возврата на прежние пять моделей достаточно выключить дополнение:

```bash
docker compose -p autoxak run --rm --no-deps --user 0 \
  api python -m app.cli.import_vehicle_catalog deactivate
```

Для возврата на предыдущий импорт вызовите `activate ПРЕЖНИЙ_SNAPSHOT_ID`.
Не удаляйте снимки SQL-командами: они сохраняют происхождение ранее выбранных
моделей. Переключение не удаляет пользователей/поездки/накопления и не запускает
`seed_fleet.py`. Отдельные новые таблицы совместимы с предыдущим кодом приложения.

## Автоматические проверки

На отдельной тестовой БД пройдено 247 серверных тестов, один тест живого staging пропущен; весь браузерный набор пройден.

Серверные регрессии проверяют отсутствие изменений прежних данных, транзакционный
откат при сбое второго пакета INSERT, конкурентный повтор импорта, пагинацию,
переключение/откат, запрещённый источник, изменение файлов пакета и начисление
денег с выбранной моделью после отключения дополнения. Браузер проверяет выбор,
обязательный расход, восстановление страницы, историю и сохранение введённого
расхода при медленном ответе каталога. Дополнительно запускается прежний набор
тестов приложения.
