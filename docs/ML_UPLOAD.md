# Испытание моделей на test.autoxak.ru

Рабочая основа, сохранённое VED-исследование и команды проверки описаны в
[ARS5_FOUNDATION.md](ARS5_FOUNDATION.md). Для read-only отчёта о версиях:
`python scripts/inspect_ml_environment.py --url https://test.autoxak.ru`;
на тестовом сервере также доступно `bash deploy/test_ml.sh versions`.
Версия локального checkout не считается подтверждением версии сервера.

Порядок проверки контейнеров, CI и критерии завершения ARS-6 описаны в
[ARS6_ML_CHECKS.md](ARS6_ML_CHECKS.md). Пока ARS-7 не закрыта, используйте на
публичном стенде только синтетические входы без реальных GPS и персональных данных.

Откройте `https://test.autoxak.ru/ml`. Вход и персональные права не нужны.
Загрузите модель, выберите поездку или JSON-файл, нажмите «Запустить тест».
Страница покажет статус, прогноз, время, ошибки Python, контрольный расход,
разницу, MAE и WAPE. Сохранённый результат можно скачать в JSON и удалить.
Стандартные записи поездок не пересчитываются; это отдельный стенд экспериментов.

## Один пакет модели

Достаточно одного ZIP с файлами в корне:

```text
model.zip
  predict.py
  weights.<ваш_формат>
```

`predict.py` обязателен. Веса и дополнительные файлы зависят от алгоритма;
для функции без внешних весов достаточно одного predict.py. Можно выбрать
и отдельные файлы вместо ZIP. До 16 файлов и 20 МиБ в распакованном комплекте.
Каталоги, ссылки, шифрованные и повреждённые ZIP не принимаются. Имена файлов
латиницей: буквы, цифры, точки, дефисы, подчёркивания, до 120 символов.

Адаптер задаёт формат весов и подготовку признаков:

```python
from pathlib import Path
# Загружайте веса относительно __file__, например:
# model_path = Path(__file__).with_name("weights.onnx")

def predict_trip(recording: dict) -> dict:
    # Подготовьте входы и вызовите свою обученную модель.
    liters = ...
    return {
        "status": "ok",
        "estimated_fuel_l": float(liters),
        "interval_started_at_ms": recording["started_at_ms"],
        "interval_ended_at_ms": recording["ended_at_ms"],
        "quality_flags": [],
    }
```

Это универсальный Python-интерфейс, а не обязательный алгоритм. В отдельном
CPU-окружении доступны NumPy, SciPy, pandas, scikit-learn/joblib и ONNX Runtime.
Точные закреплённые версии — `requirements.ml-runner.txt`. Для ONNX создавайте
SessionOptions с intra_op_num_threads=1 и inter_op_num_threads=1; для sklearn
используйте n_jobs=1. GPU и обучение больших моделей не предоставляются.

Необязательный requirements.txt внутри пакета используется для проверки
совпадения версий (строки package==version), а не установки произвольного кода.
Если нужен другой пакет, добавьте его в отдельное вычислительное окружение,
закрепите версию и пересоберите runtime. Зависимости и веса старой модели
не возвращаются в приложение. Неизвестная зависимость отображается как ошибка
выполнения, а не как успешный прогноз.

При отсутствии пригодных данных верните estimated_fuel_l=null и понятный
status. Другие поля JSON сохраняются в полном ответе модели. NaN/Infinity,
отрицательные литры и не-JSON ответы считаются ошибкой выполнения.

## Данные для теста

Загрузите экспорт поездки JSON или список до 10 таких объектов, суммарно
до 5 МиБ. Можно выбрать завершённую поездку из истории текущего браузера:
её экспорт запрашивается с существующим Bearer-токеном владельца. Без токена
можно загрузить полученный от владельца JSON. Стенд не даёт анонимный доступ
ко всем чужим GPS-записям.

Вычислитель получает schema_version, trip_id, started_at_ms, ended_at_ms,
gps, motion, vehicle, device, units и необязательные features/context.
Контроль control, прежние fuel_estimate, metrics, calculation_result и другие
готовые ответы не передаются модели. Она видит только свой снимок входов.
Timestamp — Unix ms, speed_mps — м/с, ускорения — м/с², гироскоп — градусы/с.
Пропуски остаются null; подготовка признаков версионируется в predict.py.

Для численной ошибки нужны control.same_interval=true, distance_km,
average_l_per_100km и source=trip_computer/obd/fillup. Контроль в литрах:
D_km × L_per_100km / 100. Прогноз должен явно объявить те же начальную и
конечную временные метки. При разных/неуказанных интервалах сравнение
недоступно. WAPE при нулевой сумме контроля — null. Источники указаны в
результате каждой поездки; заявленный контроль не сертифицируется стендом.

Есть ссылки «Скачать синтетический пример пакета» и «Взять пример данных».
Они позволяют проверить весь интерфейс без собственной модели. В примере
нет обученной модели и нет подтверждения дорожной точности; этот статус
явно присутствует в ответе. Его код не используется обычными поездками.

## Исполнение

Проверки идут последовательно в очереди, результаты сохраняются после
обновления страницы и перезапуска API. Снимки модели и входов фиксируются
при постановке в очередь: удаление исходного комплекта не меняет уже
созданный эксперимент. Сохраняются SHA-256 входов и файлов, Docker image ID,
вывод модели, ошибки и численные показатели. Лимиты: 20 сохранённых проверок,
5 незавершённых и 150 МиБ снимков. Старые завершённые проверки можно удалять.

API не запускает загруженный Python в своём процессе и не получает Docker
socket. Отдельный доверенный ml_controller владеет очередью и создаёт
одноразовые контейнеры фиксированного runtime-образа. Контроллер получает
Docker socket; вычисляемая модель — никогда. У контейнера модели нет сети,
секретов или БД, только read-only снимки своей модели и входов. Выход — tmpfs,
который удаляется с контейнером. Root FS read-only, UID 10001, cap-drop ALL,
no-new-privileges, 512 МиБ без swap, 0.5 CPU, 64 процесса, 128 файловых
дескрипторов, 30 секунд на проверку, CPU-time limit 15 секунд. Логи и выход
ограничены по размеру. Сбой, превышение памяти или таймаут сохраняются как
ошибка конкретной проверки; контейнер удаляется.

## Установка в существующую тестовую среду

Используются прежние `/opt/autoxak-test/.env.test`, compose.test.yml, порт
8001 и данные. Для нового checkout:

```bash
git clone --branch feat/public-test-model-manager https://github.com/kodeandr/autoXAK.git /opt/autoxak-ml-source
bash /opt/autoxak-ml-source/deploy/test_ml.sh start
bash /opt/autoxak-ml-source/deploy/test_ml.sh check
```

Если checkout уже есть:

```bash
git -C /opt/autoxak-ml-source pull --ff-only
bash /opt/autoxak-ml-source/deploy/test_ml.sh start
bash /opt/autoxak-ml-source/deploy/test_ml.sh check
```

Скрипт проверяет Docker API 1.45+, собирает отдельные api/runtime/controller
образы, делает дамп тестовой БД, обновляет только тестовый API и запускает
контроллер. После первого обновления сборка runtime может занять несколько
минут. Секреты, порт, PostgreSQL и Redis сохраняются. Production не изменяется.
Скрипт автоматически определяет группу Docker socket для UID контроллера.

```bash
bash /opt/autoxak-ml-source/deploy/test_ml.sh status
bash /opt/autoxak-ml-source/deploy/test_ml.sh logs
curl --fail https://test.autoxak.ru/api/v3/ml/runs
```

В runner.ready должно быть true. При false страница покажет причину;
отправка теста вернёт 503, а не фиктивный успех. HTTPS/Nginx остаются прежними,
client_max_body_size должен быть не менее 28m (в конфигурации из чата 150m).
Если есть отдельный Nginx gate, он не должен закрывать /ml, /api/v3/ml/ и
/static/ml.* от предусмотренного анонимного доступа. Изменения через браузер
проверяются на тот же origin; это не персональная авторизация.

`test_ml.sh check` проверяет и `/ready`, и свежий `runner.ready` с Docker image ID.
Недоступный вычислитель приводит к ненулевому коду завершения даже при здоровом API.
Эта команда не загружает модель и не создаёт эксперимент.

Для отдельного контролируемого расчёта:

```bash
bash /opt/autoxak-ml-source/deploy/test_ml.sh smoke
# Или с компьютера, имеющего сетевой доступ к тестовому стенду:
python scripts/ml_smoke.py --base-url https://test.autoxak.ru --run-synthetic
```

Создаются один синтетический комплект и одна проверка без GPS-координат.
Они сохраняются для просмотра в `/ml`; удаляйте только созданные этой командой
объекты по ID из её отчёта, когда они больше не нужны. При занятой очереди команда
отказывается начинать расчёт. Ошибка или таймаут не приводят к повторной отправке.
Прогноз 0.05 л и контроль 0.048 л — заданные тестовые числа для проверки интерфейса,
а не оценка точности модели. Production URL и переадресации не принимаются.

Хранилище autoxak-test_ml содержит комплекты, снимки проверок и отчёты.
Резервируйте его отдельно от дампа PostgreSQL и не удаляйте при обновлении.
Перед согласованной файловой копией остановите только тестовый API и контроллер.

## API и проверки

- POST /api/v3/ml/models — загрузка файлов/ZIP (JSON/base64).
- GET /api/v3/ml/models — список моделей и runnable.
- DELETE /api/v3/ml/models/{id} — удаление исходного комплекта.
- POST /api/v3/ml/runs — {model_id,data}, возвращает 202 и ID проверки.
- GET /api/v3/ml/runs — список и состояние вычислителя.
- GET /api/v3/ml/runs/{id} — полный сохранённый результат.
- DELETE /api/v3/ml/runs/{id} — удаление завершённой проверки.

При мутациях нужен X-Model-Manager: 1. Логин/пароль не требуются. Все маршруты
отключены без APP_ENV=test и ML_UPLOAD_ENABLED=true. Автоматическая активация
экспериментальной модели для обычных поездок отсутствует; старый алгоритм,
app/ml и CatBoost не возвращаются. Новое рабочее подключение выбирается после
исследования, данные поездок и reference_math сохраняются.

```bash
python -m pytest --confcutdir=tests/ml tests/ml
# С заранее собранными autoxak-ml-runtime:qa и autoxak-ml-controller:qa:
AUTOXAK_ML_DOCKER_INTEGRATION=1 python -m pytest --confcutdir=tests/ml tests/ml
PYTHON_BIN=python node tests/browser/ml_workbench.cjs
```
