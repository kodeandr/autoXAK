# Боевое развертывание autoXAK

Для ручных проверок с телефона до обновления production предусмотрена
[отдельная тестовая среда](STAGING.md) с собственными БД, ключами и HTTPS-адресом.

Сервер: Ubuntu 24.04, Docker Engine и Compose v2. Отдельный файл
`compose.production.yml` используется **самостоятельно**, без `docker-compose.yml`.
Дизайн и статические страницы не меняются.

## Переход с существующего сервера

Подтверждённая конфигурация: приложение в `/opt/autoxak`, Nginx на 80/443,
контейнеры `autoXAK_backend_api`, `autoXAK_postgres`, `autoXAK_redis`,
PostgreSQL 16 в томе `autoxak_pgdata`. Следующие шаги сохраняют этот том.
Две копии PostgreSQL нельзя запускать на одном томе одновременно.

### Готовый сценарий именно для этого сервера

После получения конфигурации Nginx для `autoxak.ru` добавлен готовый сценарий.
Выполните от root на сервере:

```bash
git clone --branch feat/production-deployment https://github.com/kodeandr/autoXAK.git /opt/autoxak-production
cd /opt/autoxak-production
bash deploy/migrate_autoxak.sh
```

Если этот каталог уже клонирован и не содержит правок, вместо `git clone`
выполните в нём `git pull --ff-only origin feat/production-deployment`.
Скрипт проверяет старые контейнеры и настройки, сохраняет действующие приватные
ключи и том `autoxak_pgdata`, собирает образ до остановки сервиса. Затем
приостанавливает запись, создаёт финальный дамп, запускает новый стек,
обновляет внутренний upstream Nginx на HTTP и проверяет HTTPS локально с
проверкой действующего сертификата. DNS и файлы Let’s Encrypt не меняются.
Копии БД, настроек и Nginx сохраняются в приватном `backups-migration-*`.

На обычной ошибке после начала переключения сценарий останавливает новый стек
перед запуском старого и восстанавливает Nginx. Если остановку нового стека
подтвердить не удалось, старый PostgreSQL не запускается, чтобы избежать
двух процессов на одном томе. Отключение питания и SIGKILL обработать trap
не может; для них используйте порядок ручного возврата ниже.

Если обнаружены старые опубликованные секреты или отсутствующий ключ подписи,
скрипт останавливается **до остановки работающего приложения**. В этом случае
сначала решите вопрос ротации, описанный ниже, а не обходите проверку.

Если старые гостевые входы можно сбросить (это согласовано для текущих тестовых
данных), используйте:

```bash
git pull --ff-only origin feat/production-deployment
bash deploy/migrate_autoxak.sh --rotate-legacy-secrets
```

Этот режим считывает фактические старые настройки из исходников контейнера
без импорта кода и без вывода секретов. Он создаёт новый ключ подписи и пароль
БД, сохраняет прежний salt Яндекса. Таблицы и поездки не удаляются; старые JWT
перестают работать, гостевой вход создаёт новый профиль. Пользователи Яндекса
повторно входят в прежний профиль. Пароль БД меняется после финального дампа,
когда старый API уже остановлен. При возврате восстанавливается и прежний
пароль, прежде чем запускать старый API. Приватный файл
`.migration-secrets.json` и его копия в каталоге бэкапа нужны для такого
возврата; они исключены из Git и Docker-контекста.

Далее описан ручной вариант того же перехода.

### 1. Подготовка без остановки приложения

Используйте отдельный каталог, чтобы старый код и конфигурация оставались доступны
для возврата. Ветка с конфигурацией: `feat/production-deployment`; после её
слияния можно клонировать `main`.

```bash
git clone --branch feat/production-deployment https://github.com/kodeandr/autoXAK.git /opt/autoxak-production
cd /opt/autoxak-production
```

Укажите реальный домен из `server_name` существующего Nginx и email администратора:

```bash
python3 deploy/prepare_existing.py YOUR_DOMAIN YOUR_EMAIL
docker compose --env-file .env.production -f compose.production.yml config --quiet
docker compose --env-file .env.production -f compose.production.yml build api
```

Скрипт сохраняет действующие ключ подписи, пароль БД, интеграции и точное имя
тома в `.env.production` с правами 600; секреты не выводятся в терминал.
Он проверяет пароль PostgreSQL по TCP. Если старый ключ отсутствует или короче
32 символов, скрипт останавливается: миграцию ключей нужно разобрать отдельно,
чтобы не потерять доступ гостевых пользователей к данным. Повторный запуск
не перезаписывает `.env.production`. Нельзя запускать `init` вместо переноса
существующих ключей.

Скрипт также останавливается, если обнаружены старые ключ подписи или пароль
PostgreSQL, ранее опубликованные в коде. Их нельзя переносить в публичный
боевой запуск. В таком случае сначала подготовьте ротацию: сохраните старый
`YANDEX_ID_SALT` (или прежний ключ как salt, если использовался fallback),
замените ключ подписи приватным и смените пароль через `\password "autoXAK_user"`
в psql. Обновите приватную конфигурацию контейнеров. Смена ключа подписи
аннулирует прежние токены: для гостевых аккаунтов сначала разберите сохранение
доступа и очередей в браузерах. Скрипт не меняет ключи и доступ пользователей
молча; при этой остановке переключение сервера продолжать нельзя.

### 2. Резервная копия перед переключением

```bash
cd /opt/autoxak-production
install -d -m 700 backups
umask 077
backup_file="backups/before-production-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker exec autoXAK_postgres pg_dump -U autoXAK_user -d autoXAK_db -Fc > "$backup_file"
docker exec -i autoXAK_postgres pg_restore --list < "$backup_file" > /dev/null
test -s "$backup_file"
```

Если любая команда завершилась ошибкой, переход не продолжать. Скопируйте дамп
и `.env.production` в приватное резервное хранилище вне этого сервера.
Сохраните также `/opt/autoxak/.env`, если файл есть, и копию действующей
конфигурации Nginx. Дамп содержит данные пользователей; не публикуйте его.

### 3. Nginx

Сохраните текущие `server_name`, сертификат и перенаправление HTTP→HTTPS.
В HTTPS-блоке сайта замените существующий `location /` содержимым
[`deploy/nginx-location.conf`](../deploy/nginx-location.conf). API теперь
работает по **HTTP на 127.0.0.1:8000**, TLS завершает Nginx. Не оставляйте
`proxy_pass https://...` от прежней конфигурации.

Подготовьте файл, но примените reload после запуска нового API:

```bash
cp -a /etc/nginx/sites-available/autoxak /etc/nginx/sites-available/autoxak.before-production
nano /etc/nginx/sites-available/autoxak
nginx -t
```

Если sites-enabled указывает в другое место, используйте фактический файл.
Не добавляйте второй `location /` и не заменяйте конфигурации других сайтов.

### 4. Переключение (короткий перерыв в работе)

Выполняйте после успешной сборки, проверки дампа и `nginx -t`:

```bash
docker stop autoXAK_backend_api autoXAK_redis autoXAK_postgres
cd /opt/autoxak-production
bash deploy/production.sh start
bash deploy/production.sh check
systemctl reload nginx
```

Старые контейнеры остаются остановленными. Новые используют тот же PostgreSQL
том, добавляют поддерживаемые столбцы при запуске и сохраняют данные.
`seed` при переходе не запускайте: он обновляет справочники и примерные цены.

Проверьте с сервера и с другого устройства:

```bash
bash deploy/production.sh status
curl --fail http://127.0.0.1:8000/ready
curl --fail https://YOUR_DOMAIN/ready
ss -lnt
```

Порты 5433 и 6379 больше не должны слушать на хосте; 8000 должен слушать
только на 127.0.0.1. Доступны публично HTTPS и SSH. Проверьте существующий вход,
историю поездок, профиль, сохранение одной поездки и выгрузку данных. Проверяйте
старый профиль в прежнем браузере, не очищая его локальные данные.

Nginx должен автоматически продлевать свой действующий сертификат. Если
используется Certbot, проверьте `systemctl status certbot.timer` и
`certbot renew --dry-run`. Публичный домен должен указывать на сервер; не
оставляйте неверную AAAA-запись, если IPv6 на сервере не настроен.

### Возврат при неудачном переключении

Сначала остановите новые контейнеры, особенно PostgreSQL:

```bash
cd /opt/autoxak-production
docker compose --env-file .env.production -f compose.production.yml stop
docker start autoXAK_postgres
# Если был подготовлен режим ротации, восстановить пароль перед старым API:
if [ -f .migration-secrets.json ]; then python3 deploy/rotate_database_password.py restore; fi
docker start autoXAK_redis autoXAK_backend_api
cp -a /etc/nginx/sites-available/autoxak.before-production /etc/nginx/sites-available/autoxak
nginx -t && systemctl reload nginx
```

Текущая миграция БД добавляет столбцы и индекс, не удаляет таблицы. Старый код
проверяйте после возврата. Если требуется восстановление именно состояния БД
до перехода, используйте проверенный дамп: это отдельная операция с остановкой
записей, которая заменяет текущие данные. Не выполняйте `down -v`, `volume rm`
или `docker system prune --volumes`.

## Новый пустой сервер

Только для новой установки без имеющихся данных и HTTPS-прокси:

1. Установите Docker Engine и Compose v2 из официального репозитория Docker.
2. Настройте DNS домена, откройте TCP 80/443 и сохраните SSH-доступ.
3. Клонируйте репозиторий, выполните:

```bash
bash deploy/production.sh init YOUR_DOMAIN YOUR_EMAIL
nano .env.production
```

Установите `COMPOSE_PROFILES=caddy`; заполните доступные интеграции. Затем:

```bash
bash deploy/production.sh start
bash deploy/production.sh seed
curl --fail https://YOUR_DOMAIN/ready
```

Caddy выпускает и продлевает публичный сертификат; его состояние хранится в
постоянных томах. Локальные `key.pem`/`cert.pem` не используются. Для нового
сервера с уже работающим Nginx профиль Caddy оставьте пустым и настройте Nginx.

## Эксплуатация

Для проверки памяти, OOM, Nginx и зависаний HTTPS с телефона используйте
инструкцию [диагностики сервера](SERVER_AUDIT.md). Сбор отчёта не требует
перезапуска или пересборки приложения.

```bash
cd /opt/autoxak-production
bash deploy/production.sh status
bash deploy/production.sh logs
bash deploy/production.sh backup
```

Для ежедневного дампа можно добавить в root crontab (`crontab -e`):

```cron
15 3 * * * cd /opt/autoxak-production && /bin/bash deploy/production.sh backup >> /var/log/autoxak-backup.log 2>&1
```

Контролируйте свободное место, ошибки бэкапа, доступность `https://DOMAIN/ready`
и срок сертификата внешним мониторингом. Docker перезапускает упавший процесс;
состояние `unhealthy` само по себе контейнер не перезапускает. Redis хранит
восстановимый кэш, не данные поездок. Дампы автоматически не удаляются:
настройте перенос во внешнее хранилище и срок хранения. Проверка `pg_restore
--list` проверяет каталог архива; полноценное пробное восстановление нужно
периодически выполнять в отдельной тестовой базе.

После слияния изменений в main и переключения серверной копии на main:

```bash
bash deploy/production.sh update
curl --fail https://YOUR_DOMAIN/ready
```

Обновление требует чистого Git, создаёт дамп перед `git pull --ff-only`,
собирает образ с тегом коммита, затем обновляет API и проверяет готовность.
PostgreSQL/Redis обновляются отдельно в согласованное окно обслуживания.
Базовые Docker-образы закреплены digest; их обновление требует изменения
конфигурации и повторной проверки, а не только команды `docker compose pull`.
Ошибка сборки не останавливает работающий API. На ошибки обновления реагируйте
по журналу; автоматический возврат миграций не выполняется.

API работает от UID 10001 с read-only файловой системой, временной директорией
и отдельным томом журналов. Доступ к Docker и `.env.production` предоставляет
доступ к секретам. Proxy headers принимаются только от адреса хостового
шлюза/Nginx и Caddy в выделенной сети, а не от произвольного клиента. Если сеть
`172.29.250.0/24` уже занята, согласованно поменяйте `PROXY_SUBNET`,
`PROXY_GATEWAY`, `PROXY_IP`, `PROXY_API_IP` и `PROXY_TRUSTED_IPS` до запуска.

Без ключей Яндекса работает гостевой вход. Для OAuth зарегистрируйте точный
`https://DOMAIN/api/v1/auth/yandex/callback`. Без ключа 2GIS используется
нейтральный дорожный контекст. Развёртывание не подтверждает точность
WearEngine: для калибровки по-прежнему нужны реальные парные логи.

## Выполненные проверки конфигурации

В облачной тестовой среде: 95 Python-тестов, браузерная проверка на production
образе, запуск API от UID 10001 с read-only FS, заполнение справочников,
перенос настроек из действующих тестовых контейнеров, сохранение специальных
символов пароля, дамп и восстановление в отдельную БД с совпадающими
счётчиками. При остановленной БД `/ready` возвращает 503, `/health` — 200;
после запуска БД готовность восстанавливается. HTTPS через Caddy проверен с
отдельно доверенным тестовым CA, включая Secure/HttpOnly OAuth-cookie.
Тесты сценария миграции подставляют ошибки сборки, дампа, запуска API,
проверки Nginx и HTTPS; проверяют порядок возврата и запрет запуска старой БД,
если остановку новой подтвердить не удалось.
Ротация пароля и его восстановление отдельно проверены на настоящем
PostgreSQL с парольной аутентификацией и ролью `autoXAK_user`. Проверка
браузера включает повторный вход после отклонения подписи JWT, сохранение
ожидающих настроек при входе Яндекса и работу прежней сессии при ответе 503.

Для сборки в облаке дополнительно использованы доверенный CA и HTTP-прокси
самой облачной среды; в конфигурацию сервера они не добавляются. Боевой Nginx,
сертификат домена, нагрузка и реальная внешняя OAuth-авторизация требуют
проверки на сервере после переключения. Успешные локальные проверки не означают,
что переключение сервера уже выполнено.
