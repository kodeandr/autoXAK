# Математическое ядро 2.0: контракт и границы достоверности

Версия численных функций: `reference-math-1`. Версия API приложения: `2.0.0`.

Это реализация проверяемых численных операций, а не свидетельство эталонной
точности смартфона, двигателя или оценки масла. Любая физическая модель имеет
область применимости и допущения. В этой версии они задаются явно; неизвестные
величины не заполняются условными коэффициентами. Численная точность и дорожная
точность проверяются разными экспериментами.

## Что удалено из рабочего расчёта

| Прежний механизм | Новое поведение |
| --- | --- |
| Базовые 1,8 л экономии на 100 км | Нет автоматической экономии по километрам |
| Скорость двойника × 1,15 и отдельно заданное ускорение | Без явной опорной траектории двойник не создаётся; расстояния проверяются |
| Множители масла за пробки и разгоны | Масло без независимо проверенной модели/измерений недоступно |
| OBD RPM/800 × условный load/temperature как «эталон масла» | По RPM определяется только длительность работы; она не является износом масла |
| 3,5 ₽ за каждый манёвр | Денежные потери по счётчику событий не вычисляются |
| Дни автономности из 4,2 л/сутки для любого водителя | Без личных данных оценка не вычисляется |
| Универсальная оценка 40..100 с фиксированными штрафами | Нет универсального физически подтверждённого индекса; возвращается null |
| Объём масла/CdA/КПД по типу кузова | Неизвестные параметры остаются неизвестными |
| Незнакомый car_id получает параметры Haval | ID сохраняется, параметры не подменяются |
| Автоматическое подтверждение H1 и p-value по синтетическим рублям | Численные ошибки сообщаются отдельно от научной верификации |

Пороги качества GPS, событий и фильтров остались параметрами алгоритмов,
зафиксированными в коде/результате. Это не калибровочные коэффициенты расхода
или химического старения. Дорожная точность детектора событий также требует
проверки. Направление движения не объявляется установленным, когда данных для
его выделения нет; неоднозначные разгоны/торможения возвращаются как null.

## Наблюдаемое и неизвестное

Приложение по-прежнему записывает исходные GPS/IMU, сохраняет черновики,
синхронизирует очередь и показывает историю. В математике поездки используются
реальные временные метки, а не предположение о неизменных 50 Гц.

- Расстояние: интеграл переданной скорости. Это точность интегрирования
  наблюдений, не подтверждение точности самих GPS-скоростей.
- Время ниже порога: длительность пересечения кусочно-линейного сигнала,
  включая части интервала; не доля количества отсчётов.
- События: пересечения порогов с длительностью и паузой в секундах.
- Перед цифровой фильтрацией сигнал интерполируется на регулярную сетку.
  Исходные записи не переписываются; расстояние интегрируется по исходной сетке.
- GPS дополнительно сохраняет выданные браузером высоту, её точность,
  направление и точность скорости, если они действительно доступны. Неизвестное
  не заменяется нулём. Отсутствие новых полей не меняет хеши старых запросов.

GPS-высота сама по себе не является точным профилем дороги. Системы отсчёта
высот GPS и карт должны быть согласованы, а вертикальная погрешность проверена.
Равнинная дорога и отсутствие ветра не предполагаются автоматически.

## Численный контракт

`app/services/reference_math.py` не читает окружение, БД, сеть и текущую дату.
Одинаковые входы дают одинаковые результаты. Единицы — SI, кроме явно названных
л/ч, литров, RPM и рублей.

Временная шкала строго возрастает, нормируется относительно первого наблюдения,
ограничена 24 часами. Значения конечны, массивы согласованы. Почти совпадающие
времена ниже численной разрешимости отклоняются. Экстраполяции за наблюдаемый
интервал нет. Ограничения входов API предназначены для численной безопасности,
а не являются нормативами вождения.

Для кусочно-линейной скорости:

    D = Σ (v[i] + v[i+1]) / 2 × Δt[i]

Время ниже порога вычисляется по точному положению пересечения на каждом
линейном отрезке. Положительная удельная кинетическая энергия:

    E_specific_positive = Σ max(v[i+1]² - v[i]², 0) / 2
    PKE = E_specific_positive / D

При D=0 PKE недоступна; фиктивный малый знаменатель не добавляется.

## Продольный баланс работы

Обязательные явно заданные параметры: полная движущаяся масса, эквивалентная
масса вращающихся частей, Crr, CdA, плотность воздуха, КПД трансмиссии и источник.
Масса должна включать водителя/груз/топливо в условиях опыта; снаряженная масса
из каталога не тождественна ей. Для каждого узла передаются высота и продольная
компонента попутного ветра. Скорость здесь — скорость вдоль пути.

    ΔE_kin = (m + m_rot) × (v1² - v0²) / 2
    ΔE_grade = m × g × Δh
    E_roll = m × g × Crr × cos(theta) × Δs
    P_drag = rho × CdA / 2 × (v - wind) × |v - wind| × v

`g=9.80665 м/с²` — стандартное ускорение свободного падения, не результат
подгонки под автомобиль. На каждом наблюдаемом сегменте высота линейна по
пройденному пути, скорость и ветер линейны по времени. Проверяется |Δh| ≤ Δs.

Работа интегрируется аналитически для этих интерполянтов. Разбиваются точки
смены знака относительной скорости воздуха и мощности на колёсах. Отдельно
вычисляются положительная и отрицательная работа, проверяется баланс:

    E_positive + E_negative = ΔE_kin + E_grade + E_roll + E_drag

Отрицательная работа не объявляется автоматически рекуперированной энергией.
Положительная работа на валу вычисляется только с переданным КПД. Перевод
механической энергии в литры по универсальному коэффициенту отсутствует.

Область модели — продольная механика при указанных параметрах. Здесь нет
полной термодинамики ДВС, динамики передач/шин/подвески, бокового ветра,
тепловой истории и модели батареи. Результат не следует называть полной
безусловной моделью автомобиля.

## Расход топлива

Поддерживаются два независимых пути:

1. Измеренный поток, л/ч, с явно заданной интерполяцией `previous` или `linear`:
   интеграл потока / 3600. Результат относится только к заданному интервалу.
2. Явно переданная прямоугольная карта `RPM × torque → л/ч`, источник карты,
   измеренные RPM/момент и логическое состояние каждого интервала.

Для карты используется билинейная интерполяция. Время разбивается по всем
пересечённым границам ячеек. Двухточечная квадратура Гаусса точна для полученного
квадратичного полинома потока. За границами карты расчёт отклоняется.
`engine_on=false` означает подтверждённое отсутствие вращения: RPM должны быть
нулевыми. Это не универсальная интерпретация положения ключа зажигания.
Отсечка топлива при вращающемся двигателе должна быть отражена в исходных
данных/карте, а не выдумана по скорости GPS.

Профиль и условия калибровки карты должны соответствовать автомобилю и опыту.
Математически правильная интерполяция не доказывает достоверность самой карты.
Источник и SHA-256 параметров сохраняются в результате.

Обученная модель расхода временно отсутствует до нового эксперимента.
Завершение записи сохраняет `fuel_estimate.status = model_not_trained` и
`null` вместо прогнозируемых литров. Явно переданные измерения и карты ДВС
по-прежнему обрабатываются этим детерминированным ядром.

## Сравнение топлива и деньги

Оба наблюдения требуют явных источников, одного vehicle_id, route_id и context_id,
одинаковых расстояния и длительности. Несовпадение не исправляется скрытым
масштабированием топлива.

    ΔF = F_reference - F_actual
    ΔC = ΔF × price_rub_per_l

Разность знаковая. Плохой результат не обрезается до нуля. Цена обязательна;
денежное округление — Decimal, половина вверх до копейки. Если обе стороны
объявили абсолютные границы погрешности, разность считается интервально
с учётом неотрицательности объёмов топлива. Границы денежного результата
округляются наружу. При неизвестной
погрешности интервал равен null, не «±0%». Это не статистический доверительный
интервал.

Даже совпадающие объявленные ID не доказывают одинаковые реальные условия или
причинный эффект стиля езды. Поэтому `causal_savings_verified=false`, и
арифметическое сравнение само по себе не меняет «копилку». Для доказанного
эффекта нужны проверяемая постановка сравнения и независимые наблюдения.

## API и воспроизводимость

Все маршруты требуют Bearer-токен владельца:

| Маршрут | Назначение |
| --- | --- |
| POST `/api/v3/math/evaluate` | Кинематика, работа, топливный поток/карта и наблюдаемая наработка |
| POST `/api/v3/math/compare-fuel` | Знаковое сравнение явных наблюдений без начисления |
| POST `/api/v3/math/validate-fuel` | Численные ошибки на объявленных контрольных записях |
| GET `/api/v3/math/trips/{session_id}/evidence` | Снимок входов и результата сохранённой поездки, только её владельцу |

В `/api/v1/telemetry/session` можно передать необязательное `reference_math`:
`{run: <контракт evaluate>, fuel_comparison: <контракт compare-fuel или null>}`.
Времена и скорости run проверяются против фактически сохраняемых GPS, либо
против legacy-телеметрии при отсутствии raw. Нельзя прикрепить результат
совсем другой траектории. Объём actual сравнения согласуется с переданным
измеренным топливным потоком, если он есть. Частичное покрытие не растягивается
на всю сессию: сохраняются фактические границы покрытия.

Исходные параметры и результат сохраняются атомарно с поездкой в отдельной
таблице `trip_math_evidence`, включая версию и SHA-256 входов. Большие карты
не загружаются вместе со списком истории. Raw-экспорт содержит ссылку и хеш.
Ошибка дополнительных математических входов/расчётов помечается как rejected;
корректная сырая запись сохраняется. Ошибка формата самого запроса по-прежнему
даёт 422. Повтор исходного запроса не создаёт повторных записей или начислений.

Примеры в `examples/reference_math/` — **синтетические численные примеры**, не
калибровочные данные. Приложение не загружает их автоматически. Для
road_energy.json известны ответы: D=100 м, работа качения 9806,65 Дж,
аэродинамическая 3000 Дж, суммарная 12806,65 Дж. Для idle_fuel_map.json
задано 0,8 л за час при нулевом пробеге. Это проверка единиц/интегрирования,
а не измеренный расход конкретного автомобиля.

## Проверка точности

MAE, RMSE, смещение и WAPE вычисляются только по переданным парам. Нулевые
контрольные значения не заменяются epsilon; WAPE при нулевой сумме контроля
равен null. MAPE по положительным значениям сопровождается числом нулевых
наблюдений. Повторные trip_id и пересечение объявленных автомобилей обучения
и проверки отклоняются. Разные источники (расходомер, ECU, БК, MAF, синтетика)
показываются раздельно. Эти проверки не удостоверяют подлинность источника.

```bash
python -m pytest tests/test_reference_math.py
python -m scripts.benchmark_suite examples/reference_math/validation.json
python -m scripts.benchmark_suite MY_REAL_DATA.json --output NEW_PRIVATE_REPORT.json
```

Пример намеренно даёт WAPE=50%, а не искусственно подтверждает точность.
Отчёт не содержит автоматической аттестации, p-value по вымышленным рублям
или подтверждённой H1 из одного удачного совпадения. Старые скрипты
псевдоверификации масла выведены из использования с явным сообщением.

Проверка этой версии: 177 Python-тестов прошли, один тест живого staging
пропущен, поскольку отдельный staging не запущен. Среди них 29 проверок нового
ядра: аналитические ответы, смена знака мощности, баланс энергии, независимость
от разбиения сетки, контроль единиц, доступа и сохранения исходных данных.
Четыре браузерных набора Chromium и отдельные проверки Service Worker прошли.
Разметка и CSS страниц сравнены с исходной версией вне блоков JavaScript.
Это автоматические проверки; они не заменяют контрольную поездку и испытания
датчиков на настоящих iOS/Android.

## Что меняется в интерфейсе и данных

Видимая разметка и CSS сохранены. Для новых неподтверждённых денег, ресурса
масла, универсального индекса и производных величин API возвращает null;
интерфейс показывает «—». Ноль остаётся нулём известной величины, а не
заменой отсутствующего измерения. Сумма уже записанной виртуальной «копилки»
не сбрасывается. Без подтверждённой экономии итог говорит о сохранении
поездки, а кнопка закрытия — «Готово»; ложное зачисление не обещается.

Старые receipt/балансы не пересчитываются и не удаляются. Их происхождение
маркируется как прежнее/непроверенное; обновление не делает старые оценки
эталонными. Нет новых автоматических начислений масла, рублей, литров или
«дней до заправки». API 2.0 меняет nullable-контракт этих полей: внешним
клиентам необходимо обработать null. Веб-клиент и Service Worker v4 обновлены.

Схема БД расширяется только таблицей trip_math_evidence через существующую
инициализацию. Удаления таблиц/данных нет. Старые канонические хеши запросов
без новых полей сохранены. Перед развёртыванием нужен обычный backup и
проверка на staging; на HOSTKEY эти изменения автоматически не установлены.

## Что требуется для дорожного эталона

Для расхода: синхронные GPS/OBD/ECU либо проверенный расходомер, точная
модификация автомобиля и условия, реальные карты двигателя или калибровка
с независимым тестовым набором. Нужны контроль покрытия, единиц, временного
сдвига, источника топлива и его погрешности.

Для состояния масла: независимо измеренное состояние/границы пригодности и
проверенная модель для данного двигателя, масла и условий эксплуатации.
RPM, нагрузка и температура важны, но сами по себе не являются лабораторным
эталоном химической деградации. Без этих данных WearEngine является только
совместимым адаптером недоступной величины и не выдаёт процент «остатка».

Сейчас проект таких реальных контрольных данных не имеет. Поэтому эта версия
даёт проверяемую основу и убирает фиктивные оценки, но не обещает подтверждённую
дорожную погрешность, полную безаппаратную физику или завершённую аттестацию.
