# Диагностика зависания сайта на телефонах

## Измерения на сервере 185.149.145.234

В присланном 22 октября 2026 года снимке: RAM 1,9 GiB, `MemAvailable` 1,3 GiB,
`used` 629 MiB, `buff/cache` 1,4 GiB. Swap 2 GiB, занято около 30 MiB;
`vmstat` за пять отсчётов показывает `si=0`, `so=0`, CPU idle 92–99%.
API использует 103,2 MiB, PostgreSQL 33,29 MiB, Redis 7,23 MiB.
Поиск OOM в журнале ядра за последние сутки ничего не вернул.

Эти измерения не показывают нехватку памяти или активную подкачку. Полоса
«2 из 2 ГБ» в панели может включать освобождаемый файловый кэш Linux.
Суммировать `used` и `buff/cache` как память, занятую приложениями, нельзя.
Наличие 30 MiB в swap само по себе не означает торможение; важны текущий
обмен, PSI, доступная память и события OOM. Пиковое потребление и лимиты
отдельного контейнера проверяются отдельно, снимок их не исключает.

## Сбор отчёта без изменения сервера

Из каталога `/opt/autoxak-production`:

```bash
python3 deploy/audit_server.py --domain autoxak.ru --observe 45
```

Скрипт использует стандартную библиотеку Python 3.9+ и имеющиеся в Ubuntu
команды. Устанавливать зависимости, пересобирать образ или перезапускать
контейнеры не требуется. Отчёт выводится в терминал и создаётся в `/tmp`
с правами 600; путь указан в начале и конце вывода. Можно задать собственный
новый путь через `--report /root/autoxak-audit.txt`; существующий файл
не перезаписывается.

Когда появится `Phone reproduction window`, откройте на телефоне
`https://autoxak.ru/ready`, затем главную страницу. В течение 45 секунд
скрипт снимает состояние памяти и TCP-соединений HTTPS каждые пять секунд.
Если уже установлен `tcpdump` и скрипт запущен от root, дополнительно
собираются текстовые заголовки не более 200 пакетов HTTPS, без вывода
содержимого пакетов или создания pcap. Отсутствие `tcpdump` не мешает сбору.
Сопоставляйте время UTC в отчёте со временем неудачной попытки.
`--observe 0` пропускает это окно.

Отчёт включает:

- доступную память, swap, CPU, IO/memory PSI, крупнейшие процессы без аргументов;
- состояние и перезапуски контейнеров, лимиты, cgroup memory.events и OOM;
- настройки памяти PostgreSQL и число соединений по состояниям без текста SQL;
- память Redis без ключей и значений, место и inode на диске;
- выбранные директивы Nginx, слушающие порты, UFW, адреса/MTU интерфейсов;
- DNS A/AAAA, ответы и задержки API напрямую и HTTPS через Nginx, отдельно
  с desktop/iPhone User-Agent, проверку сертификата TLS 1.2/1.3;
- очереди, повторные передачи TCP и доступные заголовки пакетов во время
  попытки телефона;
- OOM-события ядра и относящиеся к TLS/upstream записи стандартных логов Nginx.

Скрипт не читает `.env`, содержимое приватных ключей, полную конфигурацию
контейнеров или пользовательские записи БД. Query string, OAuth-коды,
Bearer-токены и пароли в URL удаляются из вывода. Отчёт содержит IP-адреса,
имена процессов и пути конфигурации; передавайте его владельцу проекта.
Отдельные недоступные команды не прерывают сбор. Отсутствие записи в
стандартном логе ничего не доказывает, если сайт пишет в другой файл.

## Как различать причины

1. API `/ready` не отвечает напрямую: проверять API, доступность PostgreSQL,
   перезапуски и ресурсы. Успешный `/ready` проверяет готовность API/БД, но
   не заменяет проверку всех функций.
2. API отвечает, локальный HTTPS через Nginx не отвечает: проверять TLS,
   конфигурацию виртуального хоста и `proxy_pass`. Для текущего production
   upstream должен быть `http://127.0.0.1:8000`.
3. Оба локальных пути отвечают, телефон зависает: сопоставлять DNS, соединения
   TCP и TLS с телефона, маршрутизацию и фильтрацию. Сравнение User-Agent
   проверяет серверные правила, но не эмулирует сетевой стек iPhone.
4. В access.log нет запроса: это не доказывает, что телефон не установил TCP.
   Nginx обычно пишет access.log при завершении обработки, а зависшее
   TLS-соединение ещё не содержит HTTP-запроса. Нужны TCP-состояния/логи
   соответствующего интервала.
5. Запрос телефона завершился 200 на `/ready`, а главная зависает:
   отдельно проверять загрузку HTML/JS, service worker, API и внешних ресурсов.

Растущий `memory.events oom_kill`, `State.OOMKilled=true` или запись ядра
подтверждают событие OOM, но причину конкретного зависания подтверждает
совпадение по времени. Успешная проверка TLS на самом сервере не доказывает
его доступность из мобильной сети. Самопроверка публичного адреса с сервера
также не заменяет внешнюю проверку. Сетевые параметры и лимиты памяти нужно
менять после локализации причины.

## Короткая проверка offload виртуального адаптера

Если в трассе есть повторы TCP без ACK, но счётчики и фильтры не объясняют
потери, можно сравнить передачу с программной обработкой TCP/checksum.
Наличие включённых TSO/GSO/GRO само по себе является штатной настройкой
и не доказывает неисправность драйвера или хостинга.

```bash
python3 deploy/probe_network_offload.py --interface enp3s0 --domain autoxak.ru
```

Это **временное изменение сетевых ускорений интерфейса**, максимум на окно
проверки, а не сбор только для чтения. IP, маршруты, MTU, firewall и
приложение не перенастраиваются; интерфейс не выключается. На время проверки
нагрузка CPU на обработку пакетов может увеличиться.

Скрипт сохраняет все изменяемые feature bits, проверяет отсутствие отложенных
настроек и **до изменения** заводит независимый systemd rollback timer на
180 секунд. Затем отключает доступные целевые ускорения и в течение 45 секунд
выводит TCP-состояния HTTPS. В этот момент переподключите телефон к сети
и откройте `/ready`, затем главную. После окна или обычной ошибки
исходные состояния восстанавливаются и проверяются. Независимый timer
отменяется только после подтверждённого восстановления; при обрыве SSH или
завершении Python он остаётся для восстановления. В начале также выводится
точная команда ручного возврата. SIGKILL и авария хоста могут прервать
выполнение Python; успешное срабатывание таймера зависит от работы systemd
и ethtool на хосте.

Требуются root, systemd, ethtool и ss. Если timer создать не удалось, сетевые
параметры не меняются. `--dry-run` выводит план без изменений и без timer.
Успех одного открытия не доказывает исправление: сравнивайте повторы,
очереди и результат нескольких открытий с исходными настройками.
